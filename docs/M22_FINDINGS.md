# M22 findings — mtsyc32 neighbour/prosody reconstruction

M22 continues the PC-reference conformance work, but deliberately does **not**
change production audio.  The milestone resolves several ambiguous fields in
the Windows `mtsyc32.dll`, adds portable diagnostics for the recovered neighbour
rules, and rejects two attractive but incorrect global approximations against
the 22-phrase golden corpus.

## Golden target

The fixed reference remains the 22-WAV Windows corpus generated by
`ELAN TTS Russian (Nicolai 16Khz)`.  M22 is accepted only when the default
renderer remains at least as conformant as M21.

## `0x102381d0` and `0x102382d0`

Static disassembly now gives these helpers a concrete role:

- `0x102381d0`: walk to the **previous phoneme symbol**, crossing the 0x80-byte
  outer records when necessary;
- `0x102382d0`: walk to the **next phoneme symbol**, likewise crossing records;
- both materialize a 12-byte neighbour descriptor: symbol byte at `+0`, feature
  dword at `+4`, and short metadata at `+8`.

The duration routine calls the previous walker twice and the next walker twice,
so it can inspect a two-symbol window on either side of the current phone.

See `m22_helpers_disasm.txt` and `m22_caller_disasm.txt`.

## Important correction: 0x88 / 0x89 / 0x90 / 0x93 are symbols

These bytes are not abstract feature IDs.  The DLL's CP866 table resolves them
as literal Russian phoneme symbols:

- `0x88` = И -> portable `i*`
- `0x89` = Й -> portable `j`
- `0x90` = Р -> portable `r/r'`
- `0x93` = У -> portable `u*/U*`

The adjacent transliteration table at `0x104e8ac0` maps the whole Russian phone
alphabet to the ASCII phone family used by the portable database.

M22 therefore adds `legacy_recovered_symbol()` and a corpus diagnostic scanner
instead of pretending these bytes are four generic flags.

## Recovered class strings

The DLL contains CP866 class tables used by the same prosody/phonology path:

- `БДГВЖЗЙчцщх`
- `НМРЛ`
- `ПТКСФШЧЩХЦ`

and voiced/unvoiced pairing tables such as `П<->Б`, `Т<->Д`, `К<->Г`,
`С<->З`, `Ф<->В`, `Ш<->Ж`.

`0x1075fc08` is `НМЛР`, used before one of the duration coefficients.  This
confirms that the old code uses phonological classes plus local context, not a
single global phone-class multiplier.

## Recovered `wordstr.par` context rules

The following literal-symbol comparisons are visible in the duration routine:

- adjacent Р can select `wordstr[22] = 0.90`;
- Й -> И can select `wordstr[23] = 1.20`;
- У Й У has three position-specific coefficients:
  - left У: `wordstr[25] = 0.80`;
  - Й: `wordstr[26] = 0.25`;
  - right У: `wordstr[27] = 0.80`.

These rules are surrounded by runtime/record feature gates.  Applying the
coefficients merely because the symbol pattern matches would therefore be an
unjustified approximation.

## Runtime switches

Initialization code sets one prosody feature switch off and the following six
switches on by default:

- `+0x8125c = 0`
- `+0x8125d .. +0x81262 = 1`

The duration routine also consults feature bits including `0x400` and `0x800`.
The exact semantic construction of these per-symbol bits is the remaining
missing link before the recovered `wordstr` rules can safely drive production
retiming.

## Corpus rule coverage

M22 prints a line beginning with `R` for every batch-rendered phrase.  In the
current 22-phrase reference corpus:

- Р-adjacency is exercised by several phrases;
- Й->И is not exercised;
- У-Й-У is not exercised.

This matters: the golden corpus cannot validate the large 1.20 / 0.25 / 0.80
sequence effects yet.  A later Oracle reference extension should add explicit
phrases containing those sequences once the feature gates are reconstructed.

## Rejected M22 approximations

Two candidate generalizations were tested against all 22 PC WAVs and rejected:

1. **coarse global phone-class proxy** using recovered `wordstr` values
   (vowel 1.20, sonorant 0.80, obstruent 0.90): even weak strengths reduced
   waveform correlation and did not improve the combined duration target;
2. **SEG split asymmetric retiming**: separately retiming the left/right
   diphone halves from the recovered split slot also reduced correlation and
   increased duration MAE for every useful tested strength.

A small global phone-duration retune was tested as well and degraded measured
parity.  None of these experiments are enabled in the M22 production path.

## M22 production decision

Default M22 audio is intentionally **bit-identical to M21 for all 22 reference
phrases**.  This is a positive conformance result: M22 adds verified structural
knowledge and diagnostics without exchanging a known-good waveform for a
plausible-but-worse hypothesis.

## Next

M23 should reconstruct how the record builder assigns the `0x400` / `0x800`
and neighboring feature dwords, then enable recovered `wordstr` rules only
when the same legacy predicates are satisfied.  That is the shortest path to
improving the remaining phone-level timing errors without phrase-specific
patches.
